# ADR-0014：長期使用（10 年、多台電腦）

- 狀態：**草稿**（2026-10-26 提議；第 2 部分的修正逐項以 PR 處理，需要使用者決定的項目列在最後）
- 日期：2026-10-26
- 相關需求：NFR-8、NFR-9、NFR-10、FR-37、FR-45、FR-49
- 相關：[ADR-0004](0004-usage-history.md)、[ADR-0009](0009-local-history-and-token-stats.md)（本機歷史與 Token 統計）、[ADR-0011](0011-multi-device-usage.md)（第二層）、[ADR-0012](0012-iphone-pairing.md)（配對）、[ADR-0013](0013-download-and-install.md)（內嵌 Python）

## 背景

ADR-0009 的容量估算只看一年（「整個檔案 < 50 MB」），而且用的是開發初期的紀錄量。這份 ADR 回答：同一套東西在一台 Mac（加上 Windows PC 與第二層）連續用 10 年，磁碟、效能、時間、外部變化、安全維護，以及磁碟滿、檔案損毀、寫入中斷時會發生什麼，哪些要改、哪些接受。

## 方法

兩份**互相獨立**的唯讀檢查（彼此看不到對方的結論），再由實作者逐項讀程式驗證、合併去重：

| 檢查者 | 方式 | 原始報告 |

| Codex（gpt-6.1-sol，reasoning medium，`--sandbox read-only`） | 只讀程式與文件，以假設的用量估算 | `ai-usage-monitor-work/reviews/longterm-codex.md`（L-01～L-33） |

## 決定

### 1. 去重改為時間窗（LT-01）

比時間窗舊的訊息**不計算也不記錄**，`seen_ids`／`seen_tasks`／`file_tokens` 只保留時間窗內的列。設計由 Fable 5.1（思考程度高）提出、實作者驗證，細節與「為什麼不會重複計算」的證明在 ADR-0009 第 4 節「去重時間窗」：

- 時間窗 **90 天**（與每小時資料、掃描進度的期限相同），略過界 D 每個本機日期最多前進一天、只進不退（時鐘被設到未來時，每 5 分鐘一輪也只縮一天；D 跑到今天之後時退回，見 ADR-0009 第 4 節）；去重列刪到 D − 1（多留一天吸收時區差），每次最多 2 萬列。D 在每個檔案的交易內重讀、只以資料庫目前的值前進（並行的收集器不會重複計入或讓 D 倒退）；Codex 重算把開始時的 D 凍結到讀完該檔（分輪重讀期間 D 前進也不漏算）。限制：改時區後重算含 D 前後幾小時事件的 Codex 檔，那幾小時可能多算或少算（Codex 不改寫舊 rollout，實際極少）。
- **與 `cleanupPeriodDays` 無關**：被清掉的檔案沒有東西可讀；`--resume` 副本保留原始時間戳（本機實測 311 個跨檔重複 ID），D 以前的副本必定略過、D 以後的照舊去重。
- 首次掃描與「清除並重新掃描」不套時間窗（個人紀錄的累計維持完整歷史）；完成時 D 一次設到 90 天前。
- 會漏算的只有「超過 90 天、以前從未掃到」的紀錄（還原備份、搬回舊歸檔）。真實資料庫的複本試跑：每日加總與個人紀錄和舊版完全相同。

### 2. 日誌輪替（LT-02）

收集器每次啟動時檢查日誌，超過 1 MB 就改名為 `.1`（只留一份）；Mac 的 legacy launchd 輸出（launchd 預先開好的檔案）以 `dup2` 換成新檔，內建收集器與 Windows 的 `--log-file` 在開檔前輪替；`reinstall.log` 同樣處理。每類日誌最多 2 MB。

### 3. 磁碟與資料庫維護（LT-06、LT-14、LT-20）

- 每 30 天一次（或可回收空間超過 20% 且至少 1 MB）`VACUUM`＋`wal_checkpoint(TRUNCATE)`，放在每天第一次的清理之後；清理在 `usage.json` 與上傳**之後**執行，所以維護再久也不會延誤快照與上傳。磁碟剩餘空間不到資料庫大小的 2 倍＋64 MB 時不做。
  - 時間：實測 120 MB 的資料庫 `VACUUM` 0.3 秒（Apple Silicon SSD）；時間窗上線後資料庫約 15～45 MB，遠低於這個量。這一輪可能超過 NFR-10 的「一般輪次 < 1 秒」，屬於每月一次的例外。
  - 鎖：`VACUUM` 是一個寫入交易，等待上限與其他寫入相同（busy_timeout 5 秒）；等不到時 `record_safely` 記一行、不寫 `last_vacuum_at`，隔天再試。App 的讀取連線（WAL）不擋 `VACUUM`；`wal_checkpoint(TRUNCATE)` 遇到讀取中只回傳 busy、不等待，下次 checkpoint 照常。
- 可用空間低於門檻時暫停寫歷史與 Token 統計，`usage.json` 與上傳照常；面板顯示警告。`usage.json` 寫入失敗只記一行，不中止上傳。
- 啟動時清掉 1 天以上的暫存快照檔。

### 4. 時間與並行（LT-10、LT-11、LT-16）

- Claude 重置時間沒有年份時，以「離現在最近的合理年份」推斷。
- 清理用的時間不信任突然往前跳的時鐘：每次清理最多比上次前進 2 天（時鐘往回走時用現在的時間；升級後第一次以 `last_cleanup_day` 當基準）；降採樣水位線在未來時重設；第二層的退避時間比最長退避還遠時視為到期。
- Token 統計在每個檔案的交易內重新讀取掃描進度，兩個收集器同時執行也不會重複累加。

### 5. 年度維護清單（LT-09、LT-25）

寫進 `docs/03-development-workflow.md`：每年檢查內嵌 Python 的版本與 EOL（3.13 於 2029-10 停止安全更新）、`fetch-python-runtime.sh` 的 SHA、Windows 排程的 Python 路徑、`reinstall.log` 最近成功時間；升級 macOS／Xcode 後先在 main 更新截圖基準。

## 考慮過但不採用

- **把去重 ID 存成截斷雜湊**（F-L01 的選項）：每列省 30～40%，但時間窗已經讓表有上限，不值得多一個遷移。
- **每天整份重掃取代去重表**（L-01 的「封存世代」）：首次掃描就要數小時（LT-03），不能每天做。
- **以 `fsync` 保證 `usage.json` 斷電後持久**（L-27）：快照每 5 分鐘重寫，斷電遺失最後一份只會讓下一輪補上，不值得每輪多一次同步寫入。
